# SMServer REST API v1

All v1 endpoints live under `/api/v1` on the main HTTP port (default `8741`). Responses are JSON (`application/json; charset=utf-8`) unless the endpoint returns binary data (attachments, photos, contact photos). Legacy endpoints (`/requests`, `/data`, `/send`) keep working unchanged and are documented in [REST.md](./REST.md).

The server uses a self-signed TLS certificate when `Enable SSL` is on. Use `curl -k` (or trust the certificate exported from the app) and `wss://` for the WebSocket.

## Authentication

Every endpoint except `GET /api/v1/health`, `POST /api/v1/auth/login` and `OPTIONS` preflights requires authentication. Three mechanisms are accepted, checked in this order:

1. **Bearer token** — `Authorization: Bearer <token>`. `<token>` is either
   - the **static API token** shown in the app (Settings → API). It never expires. Regenerating it in the app invalidates the old one. It can be disabled in Settings.
   - a **session token** returned by `POST /api/v1/auth/login`. It expires after 24 hours of inactivity and is forgotten when the server stops.
2. **`token` query parameter** — `?token=<token>` with the same token types. Intended for `<img src>`, `<video src>` and the WebSocket handshake, where headers cannot be set. Avoid it elsewhere: tokens in URLs end up in logs.
3. **Authenticated IP** — once a client IP has logged in (gatekeeper page, `GET /requests?password=…` or `POST /api/v1/auth/login`) every request from that IP is accepted until the server stops. This is the legacy mechanism and is what the bundled web UI relies on.

If `Require Authentication` is turned off in the app, all requests are accepted.

Token comparison is constant-time. A wrong password delays the response by two seconds.

Unauthenticated requests get `401`:

```json
{ "error": { "code": "unauthorized", "message": "Authentication required" } }
```

with `WWW-Authenticate: Bearer realm="SMServer"`.

## Errors

Every error response has the shape

```json
{ "error": { "code": "<snake_case_code>", "message": "<human readable>", "details": { } } }
```

`details` is optional. Codes and the status they come with:

- `bad_request` (400) — malformed body, unknown parameter value, missing required field
- `unauthorized` (401) — no or invalid credentials
- `forbidden` (403) — credentials are valid but the action is not allowed (e.g. typing indicators disabled, API token disabled)
- `not_found` (404) — unknown route, chat, message, attachment, photo or contact photo
- `method_not_allowed` (405) — route exists but not for this method; `Allow` header lists the valid ones
- `invalid_sender` (400) — the `from` address of a send cannot be used; see [Choosing the sender](#choosing-the-sender-from)
- `send_failed` (502) — the Messages process refused the action (send, tapback, delete, mark read); check `GET /api/v1/server/tweak`
- `tweak_unreachable` (502) — the libsmserver tweak did not answer (`GET /api/v1/senders`, `GET /api/v1/imessage-status`)
- `lookup_failed` (502) — Messages could not run the iMessage availability lookup
- `internal_error` (500) — unexpected failure; check the device log (`event=api.error` lines when debug logging is on)

## CORS

Disabled by default. Enable it in Settings → API → `Allow cross-origin requests`, optionally restricting `Allowed origins` to a comma separated list (`*` allows every origin). When enabled the server answers `OPTIONS /api/v1/*` with `204` and adds `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS`, `Access-Control-Allow-Headers: Authorization, Content-Type, X-Requested-With`, `Access-Control-Expose-Headers: Content-Disposition, Content-Range, Content-Length` and `Access-Control-Max-Age: 600`. With a restricted origin list the request `Origin` is echoed back and `Vary: Origin` is set; other origins get no CORS headers (the browser blocks them).

## Conventions

- `chat_id` is the `chat_identifier` of a conversation: a phone number in E.164 form (`+15551234567`), an email address, or `chat` followed by 16–20 digits for group chats. When `Merge contact addresses` is on, a chat may carry several addresses joined with commas (`+15551234567,person@icloud.com`); the full comma-joined string can be used as `chat_id` to merge the conversations.
- `guid` is the message GUID (`06F2E807-…`), optionally prefixed with a part identifier (`p:0/`, `bp:`), as it appears in `associated_message_guid`.
- Dates named `date`, `date_read`, `time_marker` are Apple's Messages timestamps: nanoseconds since 2001-01-01 UTC. The API also returns `*_unix` companions in seconds since 1970 (`date_unix = date / 1e9 + 978307200`). Cursors (`before`, `after`) use the Apple value.
- Path segments are percent-decoded; encode `@` as `%40` and `+` as `%2B` if your HTTP client does not do it for you (`curl` passes them through unchanged, which also works).
- Booleans in query strings accept `true`/`false`/`1`/`0`.
- Lists are paginated with `limit`/`offset` and return

```json
{ "items": [ ], "limit": 40, "offset": 0, "count": 40, "has_more": true, "next_offset": 40 }
```

`next_offset` is `null` when `has_more` is `false`.

Server, device and feature information.

```bash
curl -k -H "Authorization: Bearer $TOKEN" https://192.168.1.20:8741/api/v1/server
```

```json
{
  "name": "SMServer",
  "version": "0.9.1",
  "api_version": 1,
  "device": { "name": "iPhone", "model": "iPhone", "system": "iOS", "system_version": "16.7.16" },
  "battery": { "percentage": 83.0, "charging": false },
  "server": { "port": 8741, "secure": true, "socket_port": 8740, "socket_subdirectory": null, "web_interface": true, "uptime": 3612.4 },
  "features": { "subjects_enabled": false, "send_typing": true, "mark_when_read": true, "combine_contacts": false, "api_token_enabled": true, "cors_enabled": false, "photos": true },
  "defaults": { "chats": 40, "messages": 100, "photos": 40 },
  "theme": "dark",
  "tweak": { "reachable": true, "connected": true, "version": "1.0", "pid": 412, "capabilities": ["send", "tapback", "typing"], "watcher_listening": true, "latency_ms": 9 },

  "websocket": { "url": "wss://192.168.1.20:8740/", "events": ["hello", "new-message", "typing", "read-message", "battery-status", "pong"] }

```

`tweak` reports whether the `libsmserver` tweak inside Messages answers IPC pings (`reachable`) and whether it is hooked up (`connected`); when it is unreachable, reading works but sending, tapbacks, deleting and marking as read fail with `send_failed`. `remote` describes the optional out-of-network relay; a relay failure never prevents the local server from starting, the server retries in the background with exponential backoff and `error` carries the last failure.

### `GET /api/v1/server/tweak`

Pings the `libsmserver` tweak inside the Messages process over IPC. Use it to diagnose "messages are listed but nothing sends" situations. Same fields as `server.tweak` above plus `info`, the raw dictionary the tweak returns (`null` when unreachable).

```json
{ "reachable": true, "connected": true, "version": "1.0", "pid": 412, "capabilities": ["send"], "watcher_listening": true, "latency_ms": 12, "info": { "version": "1.0", "pid": 412, "connected": true, "capabilities": ["send"] } }
```

Body: `{"password": "…"}` as JSON, or `password=…` form-encoded. On success the caller's IP is also added to the authenticated IP list (legacy behaviour).

```bash

```

`200`:

```json
{ "token": "4f1c…", "token_type": "Bearer", "expires_at": 1761044400, "expires_in": 86400 }
```

`401` with code `unauthorized` on a wrong password (after a two second delay).

### `POST /api/v1/auth/logout`

Invalidates the session token used in the request (static API tokens cannot be logged out; regenerate them in the app). Pass `all=true` (query or JSON body) to also remove the caller's IP from the authenticated IP list, which logs out every browser on that IP.

```json
{ "ok": true }
```

Describes how the current request was authenticated.


`method` is one of `api_token`, `session`, `ip`, `disabled` (authentication turned off) or `none`.

### `GET /api/v1/chats/{chat_id}/messages`

Query:

- `limit` — default: app setting (100), min 1, max 1000
- `offset` — skip this many messages (newest first)
- `before` — only messages with `date < before` (Apple timestamp). Use the `next_before` value of the previous page to load older messages.
- `after` — only messages with `date > after`. Use the `newest_date` you have seen to catch up after a reconnect.
- `from` — `all` (default), `me`, `them` (also `0`/`1`/`2`)
- `mark_read` — `true` marks the chat as read on the device, `false` never does. When omitted the chat is marked as read only when the app setting `Automatically mark as read` is on **and** this is the first page (`offset=0` without `before`).

Items are ordered newest → oldest.

```bash
curl -k -H "Authorization: Bearer $TOKEN" "https://192.168.1.20:8741/api/v1/chats/%2B15551234567/messages?limit=50"
curl -k -H "Authorization: Bearer $TOKEN" "https://192.168.1.20:8741/api/v1/chats/%2B15551234567/messages?limit=50&before=750000000000000000"
```

```json
{
  "items": [
    {
      "ROWID": 176227,
      "guid": "06F2E807-3607-4A97-A7E8-DC2BD051DEE9",
      "chat_identifier": "+15551234567",
      "text": "Oh and here's the file",
      "subject": "",
      "is_from_me": false,
      "imessage": true,
      "date": 628153075801778048,
      "date_unix": 1606460275.8,
      "date_read": 628153077592212992,
      "date_read_unix": 1606460277.6,
      "cache_has_attachments": true,
      "attachments": [
        { "filename": "Attachments/79/09/6B094BD9-430C-4B16-8810-6E45FF409F02/clean_up.py", "mime_type": "text/x-python-script", "url": "/api/v1/attachments/Attachments/79/09/6B094BD9-430C-4B16-8810-6E45FF409F02/clean_up.py" }
      ],
      "balloon_bundle_id": "",
      "associated_message_guid": "",
      "associated_message_type": 0,
      "item_type": 0,
      "group_action_type": 0,
      "is_group": false,
      "id": "+15551234567"
    }
  ],
  "limit": 50, "offset": 0, "count": 50, "has_more": true,
  "next_before": 627285343072013056, "newest_date": 628153075801778048
}
```

Field notes:

- `text` can be empty for messages whose body is stored only in the `attributedBody` column (common on iOS 16 for messages with mentions, effects or edited text). Clients should render such messages as "no text" rather than dropping them.
- `associated_message_type` 2000–2005 are tapbacks (love, like, dislike, laugh, emphasize, question) attached to `associated_message_guid`; 3000–3005 remove them. These rows are returned inline with ordinary messages.
- `item_type != 0` or `group_action_type != 0` marks group events (member joined, name/photo changed); `item_description` may carry a human readable text.
- `balloon_bundle_id` is set for rich links (`com.apple.messages.URLBalloonProvider`, with `link_title`/`link_subtitle`/`link_type` and the preview image as attachment) and for app messages that cannot be rendered (Digital Touch, handwriting, GamePigeon).
- `sender` (display name) and `id` (handle) identify the author inside group chats.
- `is_group` tells whether the chat is a group.
- `is_sent`, `is_delivered` and `error` come from Messages: `error` is non-zero when the send failed (the red exclamation mark), and `is_delivered` turns true once the carrier or Apple reports delivery.

### `POST /api/v1/chats/{chat_id}/messages` and `POST /api/v1/messages`

Sends a message. The second form takes the chat in the body (`chat_id`) and is meant for starting new conversations: use a full phone number with country code or an email address.

Body as JSON (no files):

```json
{ "text": "Hello", "subject": "Optional subject", "photos": ["DCIM/100APPLE/IMG_0001.JPG"], "from": "me@icloud.com" }
```

`from` is optional: the address to send from, one of the `address` values of `GET /api/v1/senders`. See [Choosing the sender](#choosing-the-sender-from).

`service` is optional: `iMessage` or `SMS`. When given, the message is sent only if Messages would send this conversation over that service; otherwise nothing is sent and the response is `409 service_mismatch` with `details.current`.

Body as `multipart/form-data` (with files): fields `text`, `subject`, `photos` (colon separated camera roll paths), `from`, `chat_id` (only for `/api/v1/messages`), and any number of file parts — use the field name `attachments` (repeated) but every file part is accepted whatever its name.

Pure-JSON clients can embed files instead: `"attachments_base64": [{"filename": "note.txt", "data": "<base64>"}]`.

At least one of `text`, `subject`, `photos`, or a file is required. Original file names are kept (spaces and slashes become underscores). There is no explicit size limit; uploads of several tens of MB work, larger ones tend to fail inside Messages.

```bash
curl -k -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"text":"Hello from the API"}' "https://192.168.1.20:8741/api/v1/chats/%2B15551234567/messages"

curl -k -X POST -H "Authorization: Bearer $TOKEN" \
  -F "text=Two pictures" -F "attachments=@a.jpg" -F "attachments=@b.png" \
  "https://192.168.1.20:8741/api/v1/chats/%2B15551234567/messages"

curl -k -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"chat_id":"+15557654321","text":"New conversation"}' https://192.168.1.20:8741/api/v1/messages
```

`202`:

```json
{ "ok": true, "accepted": true, "chat_id": "+15551234567", "attachments": 2, "from": "me@icloud.com", "service": "iMessage" }
```

`from` is the address Messages queued the message from (`null` when it could not tell), `service` is `iMessage` or `SMS`.

The first send to a conversation that iOS currently has on SMS asks Messages to re-check iMessage first, which is what opening the conversation in the Messages app does. That adds up to 3 seconds once per conversation (8 seconds when `from` is given), and the message goes over iMessage if the recipient can get it.

Sending is asynchronous: the server only knows that the Messages process accepted the request. Watch the WebSocket `new-message` event (with `is_from_me: true`) to learn when it was actually sent. `400 bad_request` when the body is empty, `502 send_failed` when Messages refused it.

#### Choosing the sender (`from`)

An iPhone can send iMessages from several addresses: its own number, other numbers on the same Apple Account, and the Apple Account email addresses. `from` picks one of them for this send.

- Accepted forms: the exact `address` from `GET /api/v1/senders`, the same number without `+` or with spaces and dashes (`+82 10-1234-5678`), or the national form with a leading `0` (`010-1234-5678`). Emails are matched case-insensitively.
- It sticks: iOS stores the address on the conversation, so later sends without `from` (and sends from the phone itself) keep using it until something changes it again.
- The recipient sees the message from that address. If their contact card does not include it, it shows up as a separate conversation on their side.
- New conversations (`POST /api/v1/messages`) start from the given address.

`400 invalid_sender` when it cannot be used. `details.reason` says why, `details.available` lists the usable addresses:

- `sender_unavailable` — not one of this iPhone's addresses (or registered for iMessage)
- `sender_requires_imessage` — the conversation goes over SMS, which always uses the SIM number; pass that number or leave `from` out
- `sender_locked_group` — group conversations keep the address they started from, because changing it splits the group for the other members; `details.current` is that address
- `sender_unsupported` — Messages did not accept the address for this conversation

```json
{ "error": { "code": "invalid_sender", "message": "`from` is not one of this iPhone's iMessage or SMS addresses. GET /api/v1/senders lists them.", "details": { "reason": "sender_unavailable", "from": "other@example.com", "available": ["+15557654321", "me@icloud.com"] } } }
```

### `GET /api/v1/senders`

Addresses this iPhone can send from, read live from Messages: every validated address of every registered iMessage account, plus the SIM number for SMS.

```bash
curl -k -H "Authorization: Bearer $TOKEN" https://192.168.1.20:8741/api/v1/senders
```

```json
{
  "items": [
    { "address": "+15557654321", "type": "phone", "services": ["iMessage", "SMS"] },
    { "address": "+15550001111", "type": "phone", "services": ["iMessage"] },
    { "address": "me@icloud.com", "type": "email", "services": ["iMessage"] }
  ],
  "count": 3
}
```

`type` is `phone` or `email`. `services` says what the address can send over. Only the SIM number has `SMS`. An empty list means iMessage is off and there is no SIM number. `502 tweak_unreachable` when the tweak does not answer (it needs libsmserver 0.9.3 or later).

### `GET /api/v1/imessage-status`

Checks, without sending anything, whether recipients can receive iMessage. It asks Apple's servers the same question Messages asks before it turns a conversation blue.

```bash
curl -k -H "Authorization: Bearer $TOKEN" "https://192.168.1.20:8741/api/v1/imessage-status?address=+15551234567,someone@example.com"

curl -k -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"addresses":["+15551234567","555-123-4567","someone@example.com"]}' https://192.168.1.20:8741/api/v1/imessage-status
```

`address` (or `addresses`) is a comma separated list in the query, or `addresses` is an array in a JSON body. Up to 25 addresses per request, and duplicates are dropped. `+` does not need to be encoded in the query.

```json
{
  "items": [
    { "address": "+15551234567", "normalized": "+15551234567", "status": "registered", "imessage": true },
    { "address": "someone@example.com", "normalized": "someone@example.com", "status": "not_registered", "imessage": false }
  ],
  "count": 2,
  "timed_out": false
}
```

- `status` is one of:
  - `registered` — reachable over iMessage (`imessage: true`)
  - `not_registered` — not reachable, so a send goes over SMS (`imessage: false`)
  - `unknown` — Apple did not answer in time (`imessage: null`)
  - `invalid_address` — not a phone number or email that iMessage can address, e.g. short codes (`imessage: null`)
- `normalized` is the form that was looked up. Phone numbers in national format (`010-1234-5678`) are converted to international format using the iPhone's region.
- The first lookup of an address goes to Apple's servers (about 0.1–2 s). iOS caches the answer, so repeated lookups are fast. The tweak waits up to 8 s, and `timed_out: true` means some answers are `unknown`.
- `registered` only means the address is signed in to iMessage somewhere. It does not guarantee delivery, for example when every device of the recipient is off.
- Apple rate-limits these lookups. Do not use this for bulk lookups of address books.

`400` when no address is given or more than 25 are. `502 tweak_unreachable` or `lookup_failed` when the lookup could not run.

### `GET /api/v1/search`

Query: `q` (required), `case_sensitive` (default false), `bridge_gaps` (default true: spaces match anything in between), `group` = `time` (default, flat list newest first) or `chat` (grouped by chat).

```bash
curl -k -H "Authorization: Bearer $TOKEN" "https://192.168.1.20:8741/api/v1/search?q=dinner%20tonight"
```

```json
{
  "query": "dinner tonight",
  "group": "time",
  "items": [
    { "ROWID": 175309, "guid": "…", "chat_identifier": "+15551234567", "display_name": "John Smith", "text": "dinner tonight?", "date": 627285343072013056, "date_unix": 1605592543.1, "imessage": true, "cache_has_attachments": false }
  ],
  "chats": { },
  "contacts": [ { "chat_id": "+15551234567", "display_name": "John Smith" } ]
}
```

With `group=chat`, `items` is empty and `chats` maps `chat_identifier` → list of matching messages. `contacts` lists address book entries whose number/email contains the query.

### `GET /api/v1/contacts/match`

Query: `q` (required), `type` = `address` (default; matches phone numbers and emails) or `name`.

```json
{ "items": [ { "chat_id": "+15551234567", "display_name": "John Smith" } ] }
```

With `type=name` each item is `{ "name": "John Smith", "addresses": ["+15551234567", "john@icloud.com"] }`.

### `GET /api/v1/contacts/{chat_id}`

```json
{ "chat_id": "+15551234567", "display_name": "John Smith", "photo_url": "/api/v1/contacts/%2B15551234567/photo" }
```

`display_name` falls back to the identifier itself when there is no matching contact.

### `GET /api/v1/contacts/{chat_id}/photo`

Contact photo as `image/jpeg` or `image/png`. Group chats return the group photo when one was set. `404 not_found` when there is no photo; add `?fallback=1` to get the generic avatar instead of a 404. Use `default` as `chat_id` for the generic avatar.

### `GET /api/v1/attachments/{path}`

Raw attachment data. `path` is the `filename` value from a message's `attachments` list (relative to `/private/var/mobile/Library/SMS/`). Supports `Range: bytes=start-end` (single range, `206 Partial Content`, `Accept-Ranges: bytes`), which Safari needs for `<video>`. `Content-Disposition` is `inline`; add `?download=1` for `attachment`. HEIC images are transcoded to JPEG. `..` segments are rejected with `400`.

```bash
curl -k -H "Authorization: Bearer $TOKEN" -o out.py \
  "https://192.168.1.20:8741/api/v1/attachments/Attachments/79/09/6B094BD9-430C-4B16-8810-6E45FF409F02/clean_up.py"
```

`GET /api/v1/attachments?path=<path>` is accepted as an alternative to the path form.

### `GET /api/v1/photos`

Camera roll listing. Query: `limit` (default app setting), `offset`, `recent` (default true; `false` lists oldest first). Requires the app to have Photos permission; otherwise `items` is empty.

```json
{ "items": [ { "path": "DCIM/100APPLE/IMG_0244.JPG", "is_favorite": false, "url": "/api/v1/photos/DCIM/100APPLE/IMG_0244.JPG" } ], "limit": 40, "offset": 0, "count": 40, "has_more": true, "next_offset": 40 }
```

### `GET /api/v1/photos/{path}`

Photo data as JPEG. `path` is relative to `/var/mobile/Media/`. `404` when missing.

### Legacy endpoints

`/requests`, `/data` and `/send` accept the same `Authorization: Bearer` header and `token` query parameter as v1 in addition to IP authentication. Their payloads are unchanged; see [REST.md](./REST.md).

### Web UI assets

The bundled web interface is served from `/` (gatekeeper page when the IP is not authenticated, otherwise the app). Its assets live under `/static/<file>` (authenticated; `ETag`/`If-None-Match` supported) and the user-supplied stylesheet at `/static/custom.css`. Both HTML pages receive their runtime configuration through the literal placeholder `__SMSERVER_CONFIG__`, which the server replaces with a JSON object (`api_base`, `static_base`, `token` — a fresh session token for the authenticated browser —, `socket_port`, `socket_subdirectory`, `secure`, `theme`, `subjects_enabled`, `send_typing`, `mark_when_read`, `debug`, `version`, `defaults`, `custom_css`). `/favicon.ico` is served without authentication. The web interface (and `/static`) can be switched off in Settings; the API keeps working.

## WebSocket

The event stream runs on its own port (`socket_port`, default `8740`), `ws://` or `wss://` matching the HTTP scheme. When `WebSocket Proxy Compatibility` is on, the socket is reachable at `<scheme>://<host>/<socket_subdirectory>` through your reverse proxy instead.

Connect with `wss://192.168.1.20:8740/?token=<token>`, or with an `Authorization: Bearer` header, or from an authenticated IP. Unauthenticated connections are closed immediately after the handshake.

With the self-signed certificate, browsers must trust the certificate for the socket port separately: open `https://<host>:8740/` once and accept it.

### Envelope

Every frame is a JSON text message:

```json
{ "command": "<event>", "data": { }, "last": true }
```

Messages from the client use the same envelope with `params` instead of `data` (and an optional `id`, echoed back when a response exists).

### Server → client events

`hello` — sent right after a successful connection.

```json
{ "command": "hello", "data": { "name": "SMServer", "version": "0.9.1", "api_version": 1, "server_time": 1760958000 }, "last": true }
```

`battery-status` — sent on connect and whenever the battery level or charging state changes.

```json
{ "command": "battery-status", "data": { "percentage": 83.0, "charging": false }, "last": true }
```

`new-message` — a message was received **or sent** (check `is_from_me`). Tapbacks arrive here too (`associated_message_type` 2000–3005). `data` is a message object as returned by `GET /api/v1/messages/{guid}` plus `chat_identifier`.

```json
{ "command": "new-message", "data": { "guid": "…", "chat_identifier": "+15551234567", "text": "hi", "is_from_me": false, "date": 750000000000000000, "date_unix": 1728307200.0, "imessage": true, "attachments": [ ] }, "last": true }
```

`typing` — the other party started (`active: true`) or stopped (`active: false`) typing in `chat`.

```json
{ "command": "typing", "data": { "chat": "+15551234567", "active": true }, "last": true }
```

`read-message` — a message you sent was read by the recipient. `date` is a short relative time string, `date_read`/`date_read_unix` the timestamps.

```json
{ "command": "read-message", "data": { "guid": "…", "date": "14:03", "date_read": 750000000000000000, "date_read_unix": 1728307200.0 }, "last": true }
```

`pong` — reply to a client `ping`.

### Client → server commands

`send-typing` — tell the other party that you are typing.

```json
{ "command": "send-typing", "params": { "chat": "+15551234567", "active": true } }
```

`ping` — keep-alive; the server answers with `pong` (and echoes `id` when given).

```json
{ "id": "any-string", "command": "ping" }
```

Unknown commands are ignored and logged on the device.

### Reconnecting

The server does not buffer events. After a reconnect, fetch `GET /api/v1/chats` and `GET /api/v1/chats/{chat_id}/messages?after=<newest_date you have>` to catch up.

## Example session

```bash
HOST=https://192.168.1.20:8741
TOKEN=$(curl -sk -X POST -H "Content-Type: application/json" -d '{"password":"toor"}' $HOST/api/v1/auth/login | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')
curl -sk -H "Authorization: Bearer $TOKEN" "$HOST/api/v1/chats?limit=5"
curl -sk -H "Authorization: Bearer $TOKEN" "$HOST/api/v1/chats/%2B15551234567/messages?limit=20"
curl -sk -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"text":"hey"}' "$HOST/api/v1/chats/%2B15551234567/messages"
```
